# MAXORA — Online-First Architecture, Data Consistency & Business-Date Fix

## Phase 1–2: Audit findings and root causes (done, no code changed yet)

What I inspected: `src/lib/store.ts` (localStorage layer), `POSContext.tsx` (2959 lines, order creation/edit/cancel), `POSDataContext.tsx` (React Query facade), `RealtimeContext.tsx`, `useStoreDataSync`, `useCloudMutations`, Dexie layer (`src/lib/idb.ts`, `syncQueue.ts`, `conflicts.ts`), the `sync-orders` / `sync-store-data` edge functions, the live `public.orders` schema, and its RLS policies.

### Root causes

1. **Sales are written to localStorage first, cloud second.** In `POSContext.directBillPrint` the order is built client-side, pushed to localStorage (`addOrderToStorage`), and only then handed to `saveOrderMutation`. If the cloud call fails, the sale exists only on that device. That is exactly why Owner, Store and Cashier see different totals — each device has its own private copy of a subset of sales.

2. **The screen reads from localStorage, not the database.** `orders` state is repeatedly re-seeded from `getOrders()` (localStorage). Cloud fetch results overwrite it and vice-versa, so a refresh/logout/store-switch can visibly "lose" sales that were never in the cloud, and a device whose localStorage is cleared reports ₹0.

3. **No `business_date` column exists.** Confirmed against the live schema — `public.orders` has `created_at` only. `useBusinessDate` computes the 6 AM boundary in the browser, using the device timezone and a per-user setting, and most reports still slice by calendar midnight. A 1 AM sale therefore lands on the wrong day, and different devices disagree.

4. **No idempotency.** `sync-orders` upserts on `id` generated by the client. A retry after a network timeout with a regenerated id creates a second bill; there is no `client_transaction_id` unique constraint.

5. **No ownership/audit fields on sales.** `orders` has `cashier_id`/`cashier_name` but no `created_by_user_id`, `created_by_role`, `cancelled_by`, or `version`. Cancellation and edits are last-write-wins upserts from the client, so two devices editing one bill silently overwrite each other and there is no audit trail.

6. **The edge function trusts client money.** `sync-orders` writes `subtotal`, `tax`, `discount`, `total` straight from the request body. No server-side recalculation, no transaction spanning order + inventory.

7. **Failure and empty responses are treated as truth.** On a fetch error `sync-orders` returns `{ success: true, orders: [] }`, and the client happily renders "no sales". `clearAllOrders()` in POSContext wipes state unconditionally.

8. **Realtime is only half-wired.** `RealtimeContext` is correct (single channel per key, clean teardown) but `orders` is not driving query invalidation on other devices, so cross-device updates depend on manual refresh.

Good news: `RealtimeContext`, `POSDataContext`'s query-key namespace, and the Dexie queue are solid foundations. The fix is to invert who owns the data, not to rebuild them.

## Phase 3 — Database migration (non-destructive)

On `public.stores`: add `timezone` (default `Asia/Kolkata`) and `business_day_start_time` (default `06:00:00`).

On `public.orders`: add
- `business_date date` — backfilled from existing `created_at` using each store's start time, then made NOT NULL with a trigger that stamps it server-side on insert/update.
- `client_transaction_id text` + partial unique index on `(store_id, client_transaction_id)` — idempotency.
- `created_by_user_id uuid`, `created_by_role text`, `updated_by_user_id uuid`, `cancelled_by_user_id uuid`.
- `version integer default 1` with a trigger that increments it on update.

Indexes on `(store_id, business_date)`, `(store_id, created_at)`, `(store_id, status)`, `(cashier_id)`.

A `public.compute_business_date(ts, store_id)` SQL function is the single authority; the insert trigger calls it. Changing a store's start time never rewrites historical rows.

No data is deleted, no table is dropped, no existing column changes type.

## Phase 4 — Cloud-first sale flow

New edge function `create-sale`:
- validates JWT → resolves user → role → store (never trusts a client-supplied role or store).
- recalculates subtotal/tax/discount/total server-side from items and store tax settings.
- inserts order + payment + inventory transactions and deducts stock in one atomic RPC; any failure rolls back.
- returns the already-created sale when `client_transaction_id` repeats, instead of creating a duplicate.
- writes an `audit_logs` entry.

New RPCs `cancel_sale` and `edit_sale` (version-checked): cancelling sets `status = 'cancelled'` and records who/when/why — the row is never deleted. A stale `version` returns a conflict error rather than overwriting.

`POSContext.directBillPrint` is rewired to call `create-sale` and treat its response as truth. Local write becomes a cache update, not the source. `clearAllOrders` is removed from any automatic path.

## Phase 5 — Reads and realtime

One canonical read service `getSalesForStore(storeId, { from, to, mode })` used by every dashboard and report; role only decides the scope passed in, never the numbers. Report date filters switch to `business_date`, and "Today" means the current business day.

Orders/inventory/payments realtime events invalidate the matching React Query keys (no blind state replacement) through the existing `RealtimeContext`. On query error the previous cached data is kept and an error banner is shown — never zeroed out.

## Phase 6 — RLS

Rewrite `orders` policies around a security-definer helper that maps `auth.uid()` to its allowed store ids, replacing the current overlapping `orders_select_store` + `store_login_can_read_own_orders` pair. Cashier: insert + read own store. Store/Merchant: full store scope. Owner: their stores. Admin/Super Admin: scoped/global. Delete on `orders` is revoked outright.

## Phase 7 — Offline fallback

Dexie queue is kept but demoted: when online, cloud writes are synchronous and authoritative; the queue only holds sales taken while offline, replayed through `create-sale` with their `client_transaction_id` so replay can never duplicate. Offline data never overwrites a newer cloud row.
